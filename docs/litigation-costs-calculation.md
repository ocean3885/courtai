# 소송비용 배분 가계산 연결

작업 기준: 원격 `main`의 `fb633d2`를 확인하고 시작했다. 기존 입력 화면을 다음 단계로 확장했다.

1대1 본소의 단일 귀속 비용에는 [간편 배분 입력](litigation-costs-simple-allocation.md)을 제공한다. 사용자 적용 시 기존 계획 형식으로 연결하며 계산식·비율·절사 방식은 아래와 같다.

## 입력과 처리 범위

- **계산용 가액:** 절차·청구·당사자·상대방, 용도, 청구/항소/부대항소 구분, 금액을 구조화했다. 기존 청구별 소가 메모와 별도 보존한다.
- **산정 그룹:** 같은 절차의 가액을 합산 또는 최다액으로 묶고 공동대리 관계·청구 범위를 연결한다. 중복·흡수의 적정성은 직원이 검토하며 자동 추론하지 않는다.
- **비용별 계획:** 동일 비율 또는 입력 가중치 비례로 비용을 단계별로 나눈다. 가중치는 가액 항목·산정 그룹·직접 분수 중 선택한다. 마지막 단계에 비용 귀속자·상대방·청구·부담 관계를 명시한다.
- **정방향·역방향 비율:** 두 방향을 각각 입력한다. 기존 정방향 비율에서 `1 − 비율`로 역방향을 추정하지 않는다.
- **절사·상계:** 1원/10원 단위, 방향별 절사 후 상계/상계 후 차액 절사를 명시한다. 제111조 제2항 검토를 위한 신청인 비용만 반영하는 경로도 분리한다.

계산의 출발점은 **직원 검토 인정액 또는 선택한 별표로 산정한 자동 보수 산입액**이다. [심급별 보수 계산](litigation-costs-attorney-fees.md)을 추가했다. 환급액은 원자료 대사에 사용하며 인정액에서 다시 차감하지 않는다. 소가의 법률상 적정성, 지원 별표 외의 보수 한도·재량 조정, 기지급 차감, 결정문 확정은 수행하지 않는다.

## 결과와 검증 경로

`src/lib/litigation-costs-calculator.ts`는 BigInt 유리수로 배분·부담액·상계를 계산한다. 중간 단계는 절사하지 않는다. 입력·결과의 분자와 분모는 JSON에서 정밀도를 잃지 않도록 문자열로 보존한다.

현재 입력의 결과 표와 문서 기준값 비교표는 별개다. 결과 표는 입력이 바뀌면 다시 계산한다. 미완성·충돌·미지원 관계가 있으면 결과 전체를 보류하고 이전 금액도 숨긴다. 관계별 근거에서 아래를 확인할 수 있다.

1. 원비용과 직원 인정액
2. 산정 기초 그룹 및 자료값
3. 각 단계의 대상·가중치·분자/분모
4. 당사자 관계에 귀속된 정밀 금액
5. 적용한 방향별 부담 비율 및 상환의무
6. 방향별 합계·절사·상계 결과

각 비용의 절사 전 배분 합계가 원 인정액과 같은지 검증한다. 상환 부담이 0인 몫도 배분 검증에서는 삭제하지 않는다. 신청인 비용만 반영하는 경우 피신청인 비용의 경로는 보존하되 결과 반영에서 제외했다고 표시한다.

## 계산 보류와 한계

누락 계획·중복 계획, 없는 가액/절차/청구/당사자, 다른 절차의 가중치, 청구 범위 불일치, 미참여 당사자, 잘못된 금액·0인 분모·가중치 합계 0, 절차·청구·수임 범위와 맞지 않는 그룹, 신청비용의 부담 재판 준용 근거 누락은 계산을 보류한다.

현재는 신청인·피신청인의 쌍별 관계와 비용별 명시적 계획을 지원한다. 하나의 부담 관계에 복수 당사자나 연대 관계가 들어 있으면 자동 분해하지 않는다. 신청 대상 외 당사자의 몫을 임의로 제외하지도 않는다. 신청총액을 초과하면 상한을 임의 배분하지 않고 결과를 보류한다.

최고·자료 제출 또는 주문 효력이 미확인인 경우 선택한 설정을 가정한 가계산임을 표시한다. 기간 내 미제출이나 제111조 제2항 예외 설정과 쌍방 상계가 충돌하면 계산을 보류한다. 반환값이 가계산 가능하더라도 법률상 적정성이 확정된 것은 아니다.

절차 노드·공동대리 그룹·기존 이력 메모는 보존한다. 사건 발생 이력과 모든 소가 법리를 자동 처리하는 범용 엔진은 아니다.

## 기존 브라우저 초안의 호환성

- 저장 형식은 v2이고 저장 키는 `courtai.litigation-costs.draft.v2`다.
- v2 저장본이 없으면 기존 v1 키를 읽는다. v1 원본 키는 덮어쓰거나 삭제하지 않는다.
- v1의 기존 정보와 메모는 보존하고, 새 계산 계획·가액·그룹 및 역방향 비율은 비워 둔다. 메모에서 산식을 만들거나 기존 샘플처럼 보인다는 이유로 자동 채우지 않는다.
- 변환 내용을 검토한 뒤 사용자가 저장하면 v2로 저장한다. 새 저장본이 손상되었다면 오류를 표시하며 오래된 v1을 몰래 대신 복원하지 않는다.
- 잘못된 형식·지원하지 않는 버전·과도한 크기/깊이의 계산 트리는 복원하지 않고 현재 입력을 유지한다.

## 기준 사례 검증

기존 익명 사례에 가액 13개, 산정 그룹 8개, 비용 14개 및 명시적 계획을 연결했다. 112개 말단 배분 경로와 14개 비용의 총액 보존을 검증한다.

| 방향 | 계산한 상환액 |
|---|---:|
| A → 가 | 2,677,030원 |
| A → 나 | 4,764,820원 |
| A → 다·라 | 각 307,700원 |
| B → 가 | 2,242,480원 |
| B → 나 | 4,330,270원 |
| B → 다·라 | 각 307,700원 |

8개 금액뿐 아니라 독립 Python 재현 결과의 정밀 분수와도 대조한다. 원자료 JSON의 큰 정수를 JS Number로 읽으면 정밀도가 손실되므로 테스트에서는 해당 분자·분모를 원문 문자열로 읽는다. 제품 모델의 분수는 처음부터 문자열이다.

절사 시점을 바꾸면 A→나는 4,764,820원에서 4,764,810원으로 바뀐다. 인정액·가액·배분 계획을 바꾸었을 때 결과가 바뀌고, 알 수 없는 금액은 0과 구분되는지도 검증한다. 기존 자료의 총괄표 1원 차이와 두 번째 자료의 반소 인지대 누락 의심은 여전히 미해결이며 이번 코드에서 정답을 임의 수정하지 않았다.

테스트는 `npm test`로 실행한다. 서버 저장·Supabase 설정·인증 방식·개인회생 계산·환경 게시 상태는 변경하지 않았다.

기본 12개·특수 6개를 같은 계산 입력 형식에 연결했다. 원문 기재액 대조, 구조 재구성 사례, 미지원 보류를 구분하며 [유형별 사례 검증](litigation-costs-case-library.md)에 출처·원문 차액과 독립 검산 방법을 기록했다.
